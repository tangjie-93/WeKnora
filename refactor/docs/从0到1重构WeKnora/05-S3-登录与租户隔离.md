# `S3`：认出用户，并守住工作空间边界

[目录](./00-目录.md) · [上一章](./04-S2-数据库与迁移.md) · [下一章](./06-S4-模型配置与网关.md)

## 1. 先分清三件事

认证回答“你是谁”，租户回答“你当前在哪个工作空间”，权限回答“你在这里能做什么”。登录成功不等于可以读取所有数据，前端隐藏按钮也不等于后端已经安全。

**前置条件：** `S2` 用户、租户与成员关系结构及事务基础可用；`S0` 已采集登录成功和失败样例。

```mermaid
flowchart LR
    A[登录表单] --> B[校验凭据]
    B --> C[返回会话与用户]
    C --> D[恢复当前工作空间]
    D --> E[后续请求携带身份和租户]
    E --> F[验证成员与资源权限]
    F --> G[允许或拒绝操作]
```

## 2. 从哪些文件开始

原版源码从仓库根目录起：

| 入口 | 阅读目的 |
| --- | --- |
| `frontend/src/api/auth/index.ts` | 登录、注册、刷新、退出与当前用户请求 |
| `frontend/src/views/auth/Login.vue` | 表单和邀请注册行为 |
| `frontend/src/stores/auth.ts` | 会话恢复与当前身份 |
| `frontend/src/utils/authRefresh.ts` | 并发刷新和旧结果隔离 |
| `frontend/src/router/index.ts` | 公开页、工作空间引导和权限入口 |
| `internal/router/routes_auth_tenant.go`、`internal/handler/auth.go` | 路由、请求和失败结构 |
| `internal/middleware/`、`internal/application/access/` | 身份、租户与访问校验 |

目标文件逐个建立：后端位置相对于 `refactor/python/backend/`，包括 `app/api/v1/routes/auth.py`、`app/api/v1/schemas/auth.py`、`app/api/v1/dependencies.py`、`app/services/auth.py` 与 `app/repositories/` 下的用户和成员仓储；前端位置相对于 `refactor/python/frontend/src/`，包括 `api/auth/`、`utils/request.ts`、`stores/auth.ts`、`router/index.ts`、`views/auth/`。

复用类型放前端 `src/types/`。令牌和凭据策略按原版契约实现，不在教程中另造一套互不兼容方案。

## 3. 按顺序完成任务

### `S3.1` 完成认证契约表

**输入：** 原版认证调用和网络样例。

1. 逐项记录注册、登录、刷新、退出、当前用户接口。
2. 核对字段必填、密码约束、注册开关、邀请与错误结构。
3. 记录访问令牌、刷新令牌如何传输、保存、轮换和失效。
4. 记录无租户用户进入工作空间引导的条件，不假设每个用户永远有默认空间。

**结果：** 后端请求模式与前端类型可以依据同一份表实现。

**检查：** 普通错误密码与账户状态限制都列入，不能只采集管理员成功登录。

### `S3.2` 先实现一次后端登录

**输入：** 用户数据映射和原版密码验证规则。

1. 路由只负责参数、调用服务和协议响应。
2. 服务读取用户状态，验证密码哈希，不保存或记录明文密码。
3. 按原版要求签发令牌，并返回契约规定的用户与会话信息。
4. 使用固定测试账号验证成功、错误密码及账户受限路径。
5. 注册涉及关联记录时使用 `S2` 事务，不允许用户已写入但成员关系丢失。

**结果：** 接口测试可以得到真实会话，错误输入被拒绝。

**检查：** 日志、异常和测试报告不含原始密码或完整令牌。

### `S3.3` 建立身份和租户依赖

**输入：** 登录生成的凭据及成员关系。

1. 校验令牌有效性、过期与用户状态。
2. 从可信身份读取成员关系，再判断请求选定的工作空间是否允许进入。
3. 同时验证路径租户与当前租户关系，按原版明确处理跨租户管理员例外。
4. 为没有权限、资源不存在和未登录保留原版状态码及错误体。
5. 依赖输出可信上下文，后面的业务服务不用重新相信客户端字段。

**结果：** 受保护接口能够拒绝伪造身份和任意租户头。

**检查：** 更改 `X-Tenant-ID` 不会自动获得另一空间权限。

### `S3.4` 实现刷新和退出

**输入：** 原版刷新轮换与失效契约。

1. 实现刷新令牌校验、成功后的凭据更新和失败响应。
2. 核对退出后哪些凭据立即失效，哪些按原版寿命处理。
3. 对重放、重复刷新、过期和被撤销的会话建立测试。
4. 不把“前端删了本地令牌”当作全部退出语义。

**结果：** 会话能续期，也能按原版规则结束。

**检查：** 保存的是服务端新返回的完整凭据组合，不能只更新访问令牌漏掉轮换令牌。

### `S3.5` 建立前端请求和状态基础

**输入：** 后端接口与前端手册认证章节。

1. 安装并注册 `Pinia`、路由与普通请求客户端。
2. 在 `utils/request.ts` 集中处理身份、租户、语言、超时和错误。
3. 业务函数使用原版路径，避免客户端与函数同时添加 `/api/v1`。
4. `stores/auth.ts` 保存跨页面身份，表单值和弹窗开关保留在组件。
5. 路由守卫区分公开、受保护和无空间引导页面；恢复失败必须能展示和退出。

**结果：** 页面不用自行拼令牌头，刷新网页可以恢复真实身份。

**检查：** 状态仓库先注册再使用，页面没有依赖尚未初始化的全局数据。

### `S3.6` 复刻登录和空间交互

**输入：** `S0` 登录、注册、工作空间截图与交互记录。

1. 使用原版控件、主题和素材，还原字段、说明和操作入口。
2. 加入输入校验、提交中、错误消息和键盘焦点。
3. 登录后根据当前用户状态导航，不固定跳到一个不一定有权限的页面。
4. 恢复会话时显示明确加载状态，避免先闪出受保护内容。
5. 对比亮色、暗色、窄屏、错误和禁用状态。

**结果：** 用户可以完成注册或登录并进入正确空间。

**检查：** 成功跳转与错误停留均符合原版，按回车与鼠标点击行为一致。

### `S3.7` 处理并发刷新与切空间竞态

**输入：** 可工作的登录、刷新和请求层。

1. 同一批 `401` 只发一次刷新，其余请求等待结果。
2. 重试次数有上限；刷新接口自身失败不能递归刷新。
3. 用户退出后，旧刷新响应不能重新写回登录状态。
4. 切换空间时使旧请求和缓存失效，再加载新空间信息。
5. 延迟旧请求响应，确认不会覆盖新空间数据。

**结果：** 快速切换和令牌过期不会造成多次刷新或数据串空间。

**检查：** 同时观察实际网络请求次数和最终页面状态，不能只看一次请求成功。

## 4. 成功与失败案例

**成功：** 登录 → 查询当前用户 → 进入工作空间 → 刷新页面 → 继续操作 → 退出。每一步身份和导航一致。

**失败：** 两个用户分别属于两个空间，用甲用户凭据访问乙空间资源；同时修改路径和请求头，也应由服务端拒绝。资源业务尚未实现时，先在已有租户接口验证，`S5` 再补知识库越权。

## 5. 过关清单与排错

- [ ] 注册、登录、刷新、退出和当前用户都有契约测试。
- [ ] 错误密码、过期、撤销与重复刷新可验证。
- [ ] 身份、租户头、路径租户与资源权限独立校验。
- [ ] 会话恢复、无空间引导和路由保护可操作。
- [ ] 并发刷新、退出迟到响应与切空间竞态有测试。
- [ ] 页面关键状态截图与结果写入[进度记录](./13-进度与验收记录.md)。

| 卡点 | 优先检查 |
| --- | --- |
| 一登录就回到登录页 | 凭据保存、当前用户接口、守卫顺序 |
| 刷新请求无限循环 | 拦截器是否再次处理自身刷新失败 |
| 切空间后数据串了 | 请求头、缓存键、旧请求代际 |
| 按钮隐藏但接口仍可调用 | 后端授权依赖和资源归属条件 |

自测：用户已经登录，为什么还必须检查每个资源的访问权限？
