# `S3`：认出用户，并守住工作空间边界

[目录](./00-目录.md) · [上一章](./04-S2-数据库与迁移.md) · [下一章](./06-S4-模型配置与网关.md)


## 1. 先分清三件事

认证回答“你是谁”，租户回答“你当前在哪个工作空间”，权限回答“你在这里能做什么”。登录成功不等于可以读取所有数据，前端隐藏按钮也不等于后端已经安全。

**前置条件：** `S2` 用户、租户与成员关系结构及事务基础可用；`S0` 已采集登录成功和失败样例。

```mermaid
flowchart LR
    A[登录表单] --> B[校验凭据]
    B --> C[返回会话与用户]
    C --> D[恢复当前工作空间]
    D --> E[后续请求携带身份和租户]
    E --> F[验证成员与资源权限]
    F --> G[允许或拒绝操作]
```

## 2. 从哪些文件开始

原版源码从仓库根目录起：

| `frontend/src/views/auth/Login.vue` | 表单和邀请注册行为 |
| `frontend/src/stores/auth.ts` | 会话恢复与当前身份 |
| `frontend/src/utils/authRefresh.ts` | 并发刷新和旧结果隔离 |

| `internal/middleware/`、`internal/application/access/` | 身份、租户与访问校验 |

目标文件逐个建立：后端位置相对于 `refactor/python/backend/`，包括 `app/api/v1/routes/auth.py`、`app/api/v1/schemas/auth.py`、`app/api/v1/dependencies.py`、`app/services/auth.py` 与 `app/repositories/` 下的用户和成员仓储；前端位置相对于 `refactor/python/frontend/src/`，包括 `api/auth/`、`utils/request.ts`、`stores/auth.ts`、`router/index.ts`、`views/auth/`。

复用类型放前端 `src/types/`。令牌和凭据策略按原版契约实现，不在教程中另造一套互不兼容方案。

## 3. 按顺序完成任务

### `S3.1` 完成认证契约表

**输入：** 原版认证调用和网络样例。

1. 逐项记录注册、登录、刷新、退出、当前用户接口。
2. 核对字段必填、密码约束、注册开关、邀请与错误结构。
3. 记录访问令牌、刷新令牌如何传输、保存、轮换和失效。
4. 记录无租户用户进入工作空间引导的条件，不假设每个用户永远有默认空间。

#### 从一次点击拆出认证输入和输出

先打开原版登录页，网络面板只看一次登录请求；再沿前端请求函数找到后端路由。契约是前后端共同遵守的约定，不等于自己设计一份看起来合理的结构。

1. 在 `api-contract.md` 单独记录成功登录、错误密码、受限账号；标明哪些字段给用户看，哪些凭据必须脱敏。
2. 继续记录当前用户、刷新、退出，将每次请求使用的身份来源连成时间线。
3. 在 `app/api/v1/schemas/auth.py` 逐字段建立输入、输出模式；前端 `src/types/` 使用同一字段含义。不要把登录返回与当前用户返回默认当成相同结构。
4. 请求字段错误时，比较原版状态码和错误正文；框架默认校验错误若不同，应在协议边界适配。

**检查方法：** 先用脱敏样例验证序列化结果，再实现业务。账号不存在与密码错误的对外差异是否允许暴露，由原版契约和安全策略共同核对，不自己增加泄露账号存在性的提示。

**结果：** 后端请求模式与前端类型可以依据同一份表实现。

**检查：** 普通错误密码与账户状态限制都列入，不能只采集管理员成功登录。

### `S3.2` 先实现一次后端登录

**输入：** 用户数据映射和原版密码验证规则。

1. 路由只负责参数、调用服务和协议响应。
2. 服务读取用户状态，验证密码哈希，不保存或记录明文密码。
3. 按原版要求签发令牌，并返回契约规定的用户与会话信息。
4. 使用固定测试账号验证成功、错误密码及账户受限路径。
5. 注册涉及关联记录时使用 `S2` 事务，不允许用户已写入但成员关系丢失。

#### 先写登录服务，再接路由

密码哈希是专用于验证密码的保存形式，不是可逆的明文备份。复用与原版记录兼容的密码库，不自行用普通内容哈希替代。

1. 用户仓储先提供按原版登录标识查询的方法，输入查询值，输出用户记录或不存在；不在仓储签发令牌。
2. `app/services/auth.py` 接收已校验输入，调用仓储，按原版顺序检查账号状态与密码；任何拒绝路径都不产生可用会话。
3. 校验通过后调用专门的凭据签发逻辑，使用原版要求的身份、有效期和相关字段；不要直接把用户数据库对象整体编码后返回。
4. 若会话或刷新记录需要保存，在事务成功后再构造对外响应；记录保存失败不能仍发给浏览器可用凭据。
5. 路由接收请求模式、调用服务，将结果转为响应模式；密码、哈希与内部敏感字段不会自动跟随实体泄露。
6. 先通过接口测试获取会话，再调用当前用户接口确认身份一致，最后才连接页面。

**失败检查：** 错密码、受限账号、凭据记录保存失败各测一次，断言没有可用会话和残留写入。找不到用户是业务拒绝，数据库断开是系统故障，两类内部原因不能混为一谈。

**结果：** 接口测试可以得到真实会话，错误输入被拒绝。

**检查：** 日志、异常和测试报告不含原始密码或完整令牌。

### `S3.3` 建立身份和租户依赖

**输入：** 登录生成的凭据及成员关系。

1. 校验令牌有效性、过期与用户状态。
2. 从可信身份读取成员关系，再判断请求选定的工作空间是否允许进入。
3. 同时验证路径租户与当前租户关系，按原版明确处理跨租户管理员例外。
4. 为没有权限、资源不存在和未登录保留原版状态码及错误体。
5. 依赖输出可信上下文，后面的业务服务不用重新相信客户端字段。

#### 把不可信请求变成可信上下文

依赖是路由执行前共同做的准备动作。本阶段需要的输出是已经验证的用户与空间信息，不能只返回浏览器提交的标识。

1. 在 `app/api/v1/dependencies.py` 从契约规定的位置读取凭据，验证完整有效性；只解码内容不算验证。
2. 用验证得到的身份读取当前账号状态，拒绝失效或受限情况。
3. 读取请求选择的空间，再用成员仓储和原版管理员规则确认是否允许进入；空间头只表示选择，不授予权限。
4. 将可信用户、空间及必要权限信息交给服务。服务再校验目标资源和具体操作；已登录不意味着可以访问任意资源。
5. 先把依赖挂到一个已有受保护接口，分别发送无凭据、伪造凭据、合法凭据以及伪造空间选择。

**可见结果：** 只有允许路径进入业务查询，拒绝路径不返回资源正文。资源不存在和无权访问对外是否区分按原版处理，日志也不能泄露无权资源内容。

**结果：** 受保护接口能够拒绝伪造身份和任意租户头。

**检查：** 更改 `X-Tenant-ID` 不会自动获得另一空间权限。

### `S3.4` 实现刷新和退出

**输入：** 原版刷新轮换与失效契约。

1. 实现刷新令牌校验、成功后的凭据更新和失败响应。
2. 核对退出后哪些凭据立即失效，哪些按原版寿命处理。
3. 对重放、重复刷新、过期和被撤销的会话建立测试。
4. 不把“前端删了本地令牌”当作全部退出语义。

#### 为凭据轮换画出读旧、写新、废旧的顺序

刷新可能同时改变访问凭据和刷新凭据。“轮换”表示旧凭据按规则失效、新凭据接替，而不只是修改浏览器中的一段字符串。

1. 先在服务中验证旧刷新凭据及关联会话，查清原版的重复使用处理方式。
2. 按原版事务与并发规则生成新状态、使旧状态失效；并发请求不能都凭同一个旧状态完成不允许的更新。
3. 保存成功后才返回完整新凭据组合，前端一次性更新，避免新旧组合混用。
4. 退出入口按契约处理服务端状态，再由前端清理身份和敏感缓存；服务端失败时也应有明确反馈。
5. 测试刷新前、刷新后、退出后的受保护请求，并再次使用旧刷新凭据，逐项比对原版结果。

**排查：** 刷新后立刻失效先看是否漏存轮换后的凭据；退出后旧响应恢复登录则留到 `S3.7` 加代际隔离，不能只把跳转写得更快。

**结果：** 会话能续期，也能按原版规则结束。

**检查：** 保存的是服务端新返回的完整凭据组合，不能只更新访问令牌漏掉轮换令牌。

### `S3.5` 建立前端请求和状态基础

**输入：** 后端接口与前端手册认证章节。

1. 安装并注册 `Pinia`、路由与普通请求客户端。
2. 在 `utils/request.ts` 集中处理身份、租户、语言、超时和错误。
3. 业务函数使用原版路径，避免客户端与函数同时添加 `/api/v1`。
4. `stores/auth.ts` 保存跨页面身份，表单值和弹窗开关保留在组件。
5. 路由守卫区分公开、受保护和无空间引导页面；恢复失败必须能展示和退出。

#### 请求层先做到一个地方加身份

`src/api/auth/` 描述具体接口，`utils/request.ts` 处理每次请求共用的规则，`stores/auth.ts` 保存页面之间共享的身份。这三层不互相复制同一套刷新逻辑。

1. 初始化应用时先注册状态仓库和路由，再使用依赖它们的请求逻辑；避免模块加载时读取未初始化状态。
2. 普通请求实例只在一个地方设置基础前缀、超时和通用头；业务函数只填写剩余路径与请求内容。
3. 发请求时读取当前凭据和空间，不能在创建客户端时永久捕获旧值。
4. 先实现登录和当前用户两个函数；按响应的实际层级取值，不额外添加或去掉 `data` 外壳。
5. 应用启动进入“正在恢复身份”，完成当前用户查询后再决定路由；网络故障与明确凭据失效按原版分开处理。

**验证：** 网络面板检查路径没有重复前缀，身份来自统一入口；刷新页面后只有确认当前身份才显示受保护内容。接口返回数据但页面空白时，先检查类型和响应解包位置。

**结果：** 页面不用自行拼令牌头，刷新网页可以恢复真实身份。

**检查：** 状态仓库先注册再使用，页面没有依赖尚未初始化的全局数据。

### `S3.6` 复刻登录和空间交互

**输入：** `S0` 登录、注册、工作空间截图与交互记录。

1. 使用原版控件、主题和素材，还原字段、说明和操作入口。
2. 加入输入校验、提交中、错误消息和键盘焦点。
3. 登录后根据当前用户状态导航，不固定跳到一个不一定有权限的页面。
4. 恢复会话时显示明确加载状态，避免先闪出受保护内容。
5. 对比亮色、暗色、窄屏、错误和禁用状态。

#### 表单提交拆成六个可观察动作

先使用原版登录组件结构，不同时重写全局导航。局部表单值属于当前页面，成功后的用户身份才进入共享仓库。

1. 定义输入值、提交中状态和错误信息；使用原版规则做即时提示，后端仍独立验证。
2. 点击或回车进入同一提交函数；检查是否已有提交进行，防止两个入口发两次请求。
3. 发出请求前清理上次错误、锁定提交按钮；失败时保留输入并显示允许展示的错误。
4. 成功后保存服务端认可的身份数据，读取必要的当前用户和空间状态。
5. 根据状态去目标页面或无空间引导；不要先跳转再补身份，造成页面闪现或循环跳转。
6. 收尾释放提交状态；恢复会话的加载状态与用户主动提交的状态分开。

**验证：** 断网时表单仍可看见输入；恢复网络再次提交可成功；键盘焦点与原版一致。登录成功却立即回登录页时，先比对凭据保存与守卫读取的时机。

**结果：** 用户可以完成注册或登录并进入正确空间。

**检查：** 成功跳转与错误停留均符合原版，按回车与鼠标点击行为一致。

### `S3.7` 处理并发刷新与切空间竞态

**输入：** 可工作的登录、刷新和请求层。

1. 同一批 `401` 只发一次刷新，其余请求等待结果。
2. 重试次数有上限；刷新接口自身失败不能递归刷新。
3. 用户退出后，旧刷新响应不能重新写回登录状态。
4. 切换空间时使旧请求和缓存失效，再加载新空间信息。
5. 延迟旧请求响应，确认不会覆盖新空间数据。

#### 用受控顺序验证并发，不靠快速手点碰运气

代际是当前身份状态的一次版本号；退出或切换后版本前进，旧请求即使晚到，也失去更新当前状态的资格。

1. 请求层保存当前共享刷新任务；首个符合条件的失败创建任务，后续请求等待同一个结果。
2. 将刷新请求排除在自动刷新逻辑外，并标记已重试请求；仍失败时停止循环。
3. 刷新开始时记录身份代际，返回时先比较；不匹配就丢弃状态更新，不能让退出后的浏览器重新登录。
4. 切空间前使旧资源请求失效或取消，清理旧范围缓存，之后才发新空间请求；仅改请求头不够。
5. 在测试中让两个普通请求先失败，暂停刷新响应，断言刷新只有一次；再完成刷新并核对各请求的最终结果。
6. 另测刷新未结束时退出、旧空间请求未返回时切换；放行旧响应后仍保持退出或新空间状态。

**边界：** 凭据刷新成功不自动授权重放所有写操作。是否重放按请求是否被服务端接受及原版规则决定，尤其不能无条件重复生成或支付类操作。

**结果：** 快速切换和令牌过期不会造成多次刷新或数据串空间。

**检查：** 同时观察实际网络请求次数和最终页面状态，不能只看一次请求成功。

## 4. 成功与失败案例

**成功：** 登录 → 查询当前用户 → 进入工作空间 → 刷新页面 → 继续操作 → 退出。每一步身份和导航一致。

**失败：** 两个用户分别属于两个空间，用甲用户凭据访问乙空间资源；同时修改路径和请求头，也应由服务端拒绝。资源业务尚未实现时，先在已有租户接口验证，`S5` 再补知识库越权。

## 5. 过关清单与排错

- [ ] 注册、登录、刷新、退出和当前用户都有契约测试。
- [ ] 错误密码、过期、撤销与重复刷新可验证。
- [ ] 身份、租户头、路径租户与资源权限独立校验。
- [ ] 会话恢复、无空间引导和路由保护可操作。
- [ ] 并发刷新、退出迟到响应与切空间竞态有测试。
- [ ] 页面关键状态截图与结果写入[进度记录](./13-进度与验收记录.md)。

| 卡点 | 优先检查 |
| --- | --- |
| 一登录就回到登录页 | 凭据保存、当前用户接口、守卫顺序 |
| 刷新请求无限循环 | 拦截器是否再次处理自身刷新失败 |
| 切空间后数据串了 | 请求头、缓存键、旧请求代际 |
| 按钮隐藏但接口仍可调用 | 后端授权依赖和资源归属条件 |

自测：用户已经登录，为什么还必须检查每个资源的访问权限？
