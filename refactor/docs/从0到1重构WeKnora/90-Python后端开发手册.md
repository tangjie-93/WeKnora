# 用 `Python` 从零实现 `WeKnora` 后端：从第一个接口到完整产品

[返回目录](./00-目录.md) · [详细实施步骤](./00-目录.md) · [进度记录](./13-进度与验收记录.md)

先读[总路线](01-总路线与学习方法.md)，再按当前阶段阅读本文。页面实现看[前端指南](91-Vue与Tailwind前端开发手册.md)，查找原版页面和交互看[功能与源码地图](92-知识词典与原版功能地图.md)。本目录所有章节统一使用 `S0–S10`，不用再换算另一套阶段编号。

本文负责回答：“用户点下按钮以后，后端应该怎样处理？”目标是自己建立 `Python` 实现，保留原版数据库结构、接口和产品行为。这里的“重构”指实现语言的替换；本轮学习不要求安排旧系统生产切流。

**先分清现状和计划：** 本次整理时，`refactor/python/` 尚不存在。下文的 `app/`、测试、任务脚本都是你将逐步创建的文件，不代表已经完成。原版代码已存在，供核对需求、协议和业务规则。本文所有源码路径以仓库根目录 `WeKnora/` 为起点；命令会另行说明工作目录。

## 1. 先懂一条请求，不急着懂整个架构

假设用户在页面上创建“公司手册”知识库：

1. 浏览器把名称和配置发给后端。
2. 后端确认用户身份、当前工作区，以及是否允许创建知识库。
3. 检查模型是否存在、是否可用，名称和配置是否合法。
4. 把记录写入数据库；失败时撤销未完成的写入。
5. 按原版接口格式返回结果，前端展示新的卡片。

把这些工作拆开，不是为了多写文件，而是为了方便找问题：

| 名称 | 用大白话解释 | 在目标工程中放哪里 |
| --- | --- | --- |
| 路由 `route` | 接收请求，返回响应 | `app/api/v1/routes/` |
| 依赖 `dependency` | 在办事前确认身份、准备数据库连接 | `app/api/v1/dependencies.py` |
| 数据模式 `schema` | 规定请求和响应允许有哪些字段 | `app/api/v1/schemas/` |
| 服务 `service` | 决定业务上该怎样做 | `app/services/` |
| 仓储 `repository` | 负责数据库的查询和写入 | `app/repositories/` |
| 外部集成 `integration` | 调用模型、文档解析等外部能力 | `app/integrations/` |

开始时只建当前用得到的文件。健康检查不需要仓储；知识库增删改查才需要数据库。不要为了目录整齐给每一行代码套一层类。

## 2. `S0`：把原版当成有答案的练习题

### 2.1 到哪里找答案

先固定原版提交号。后续原版更新时，不要一边学习一边悄悄改变“完全一致”的参照物。

在仓库根目录执行：

```sh
git rev-parse HEAD
git status --short
```

| 想知道什么 | 先看哪里 | 然后看哪里 |
| --- | --- | --- |
| 一个接口到底叫什么 | `internal/router/` | `frontend/src/api/` 的调用 |
| 接口接受和返回什么 | `internal/handler/`、`internal/types/` | 浏览器网络面板中的实际请求 |
| 为什么允许或拒绝操作 | `internal/router/rbac.go`、`internal/middleware/` | `internal/application/access/`、对应服务 |
| 数据库有哪些字段 | `migrations/sqlite/`、`migrations/versioned/` | `internal/types/`、仓储实现 |
| 迁移如何记录成功和失败 | `internal/database/migration.go` | 同目录迁移测试 |
| 文件如何解析 | `docreader/README.md`、`docreader/main.py` | `docreader/parser/`、`docreader/client/` |
| 聊天数据怎么逐段发送 | `internal/types/chat.go` | `internal/handler/session/stream.go` |

这里的迁移脚本位于仓库根的 `migrations/`，并不在 `internal/database/` 下面。原版主要业务服务使用 `Go`；已有的 `docreader` 是可复用的 `Python` 文档解析服务。

### 2.2 先记录一个接口，而不是一次抄完所有接口

从注册或知识库列表开始，在学习记录中填写：

```text
页面动作：
HTTP 方法和完整路径：
请求头及身份要求：
请求字段、必填项和默认值：
成功响应原文：
失败状态码及响应原文：
分页、排序、时间和空值格式：
涉及的表和权限规则：
原版源码路径、提交号：
新实现测试、页面验收证据：
```

“契约”就是上面这份约定。字段同名但空值不同，或原版返回数组而新接口多包了一层 `data`，都会让页面出问题。不要强行为全部接口制定一种新的响应外壳。`FastAPI` 默认参数错误响应也未必与原版一致，需要对照后适配。

**本阶段产出：** 总路线中的基线记录和第一组脱敏请求样例。运行原版是采集参照，不是让新系统永久依赖旧后端。

**过关条件：** 能用自己的话说清一次请求的输入、输出、权限和落库位置。只有路由名、没有响应样例，还不能开始实现该接口。

## 3. `S1`：今天先让一个接口真的跑起来

### 3.1 准备环境和目录

使用 `Python 3.12+`。下面是 `macOS / Linux` 的终端命令；从 `refactor/` 目录开始。如果将来目录里已有实现，先检查文件，不能覆盖已有工程。

```sh
python3 --version
mkdir -p python/backend/app python/backend/tests/unit
cd python/backend
python3 -m venv .venv
source .venv/bin/activate
```

`Windows PowerShell` 激活命令为 `.\.venv\Scripts\Activate.ps1`。后续命令中的 `python` 应指向虚拟环境，而不是系统解释器。

新建 `pyproject.toml`，先声明本课会用到的依赖：

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "weknora-python-backend"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["fastapi", "uvicorn[standard]"]

[project.optional-dependencies]
dev = ["pytest", "pytest-asyncio", "httpx", "ruff"]

[tool.setuptools.packages.find]
include = ["app*"]

[tool.ruff]
target-version = "py312"
line-length = 110
```

新建空文件 `app/__init__.py`，然后新建 `app/main.py`：

```python
from fastapi import FastAPI

app = FastAPI(title="WeKnora Python")


@app.get("/health")
async def health() -> dict[str, str]:
    return {"status": "ok"}
```

在 `python/backend/` 中执行：

```sh
python -m pip install -e '.[dev]'
python -m uvicorn app.main:app --reload --port 8080
```

另开终端检查：

```sh
curl -i http://127.0.0.1:8080/health
```

应看到状态码 `200` 和 `{"status":"ok"}`。这一响应与原版健康检查一致。开发时还可以打开 `http://127.0.0.1:8080/docs` 查看接口说明；它是开发工具，不是要复刻的产品页面。

这里用 `async def` 表示接口可以等待数据库或网络返回。它不会自动让耗时计算变快；后面的文档解析不能因此直接塞进请求线程。

### 3.2 留下一个能重复执行的检查

新建 `tests/unit/test_health.py`：

```python
from fastapi.testclient import TestClient

from app.main import app


def test_health() -> None:
    with TestClient(app) as client:
        response = client.get("/health")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}
```

在已激活虚拟环境的后端终端中运行：

```sh
python -m pytest -q
python -m ruff check .
```

前端在 `5400` 端口通过代理调用这个接口，具体配置见前端指南。原版若占用 `8080`，先决定运行哪一个服务；不要以为页面连到原版就证明新后端成功了。

**本阶段产出：** 上述文件、成功响应和测试结果。将实际安装版本写入项目选定的依赖锁定文件，后续按锁安装；上面的最小配置本身不是可重复安装的版本锁。

**过关条件：** 前端能看到新服务状态；停掉后端后，页面明确显示连接失败。`S1` 只证明请求通了，不代表知识库已经实现。

**常见卡点：** `ModuleNotFoundError` 先检查工作目录和虚拟环境；连接拒绝先检查端口；浏览器失败而 `curl` 成功时再检查代理地址。

## 4. `S2`：让数据在重启以后还在

数据库像一本长期保存的账本。表描述记录结构，迁移记录“账本结构怎样变化”，事务保证一次操作要么整体成功，要么整体撤销。

### 4.1 先读结构，再写映射

先用 `SQLite` 做本地练习，随后用 `PostgreSQL` 验证生产行为。两者使用原版各自的迁移目录；不能把 `PostgreSQL` 的脚本直接交给 `SQLite`。

1. 阅读原版用户、租户、成员关系、模型和知识库对应的建表与后续变更。
2. 为这些表记录字段、主键、索引、唯一约束、默认值、软删除和时间格式。
3. 在 `app/core/database.py` 建立 `SQLAlchemy 2` 异步连接和会话；在 `app/domain/entities/` 建立对应映射。
4. 只连接独立学习数据库，先完成插入、读取和失败回滚实验。
5. 增加迁移入口，按原顺序执行相应数据库的迁移，并记录执行状态。

到这一步才添加 `SQLAlchemy` 和相应异步驱动。增加依赖后同步锁定版本。

**不要把自动建表当作迁移系统。** `metadata.create_all()` 不能证明字段变更、索引和原版迁移历史兼容。若复用原版版本表，需理解 `schema_migrations` 的版本和失败标记语义；发生失败要中止，不能清除标记假装成功，也不能让另一套迁移工具擅自重解释已有版本。

### 4.2 做一次故意失败的练习

在测试数据库的一次事务里创建两条有关联的记录，让第二步违反约束。检查第一步的写入是否也被撤销。这样才能理解“回滚”不是打印一条错误日志。

**产出：** 数据库连接、最小实体映射、迁移入口和 `tests/contract/test_migrations.py`。这些文件需要新建；仓库说明里提到的阶段脚本不能在尚未创建时直接运行。

**过关条件：** 空库初始化成功，重复迁移不重复执行，迁移失败停止，事务失败不留半条业务记录。`SQLite` 通过后，在 `S10` 前用 `PostgreSQL` 复核字段类型、约束、排序和事务行为。

## 5. `S3`：先认出用户，再允许他操作数据

“登录”证明你是谁；“租户”决定你正在使用哪个工作区；“权限”决定你在这个工作区可以做什么。这三件事不能只靠页面隐藏按钮完成。

先阅读 `internal/router/routes_auth_tenant.go`、认证处理器及中间件。原版存在 `/api/v1/auth/register`、`/api/v1/auth/login`、`/api/v1/auth/refresh`、`/api/v1/auth/logout`、`/api/v1/auth/me`，但仅知道路径还不够，必须补齐 `S0` 的请求和响应样例。

动手顺序：

1. 在认证请求模式中实现与原版一致的字段校验。
2. 在服务里完成密码哈希验证、用户状态检查和令牌签发。密码不能明文存储；需要读取原版密码记录时核对哈希算法兼容性。
3. 在认证依赖中验证令牌、有效期和账户状态，得到可信身份。
4. 根据身份和成员关系确认当前租户；不能直接信任浏览器传来的 `X-Tenant-ID`。
5. 按原版实现刷新、退出及失效行为，再连接前端注册和登录页。
6. 在每个资源查询中同时检查资源归属和操作权限；成员管理、共享资源等细节在 `S9` 补齐，隔离基础现在就做。

**新增位置：** `app/api/v1/routes/auth.py`、相应请求模式、`app/services/auth.py`、用户仓储和认证依赖。先用最简单的一次登录走完这些层，再处理刷新并发。

**验收练习：** 建两个用户和两个工作区。用户甲登录后，将知识库请求里的标识改成用户乙的资源，必须被拒绝。再测试错误密码、重复注册、过期令牌、退出后访问、刷新失败。

**常见卡点：** 只按资源主键查数据库会产生越权；只在登录时检查成员关系会漏掉后来被移除的成员。拒绝时的状态码和错误体仍按原版契约处理。

## 6. `S4`：先用假模型理解模型调用

三种模型先记住用途：聊天模型写回答；向量模型把文本转换成可比较的数字列表；重排模型把候选资料重新排队。它们不是同一个“模型名称”字段随意互换。

先在 `app/integrations/` 建一个确定性的测试实现：同一输入始终返回同一答案或同一向量。这样测试失败时，不用猜是代码有错还是模型今天换了一种说法。假模型只是教学和测试替身，不代表检索质量已达到原版。

1. 对照原版模型接口和配置页面，实现模型记录的增删改查。
2. 校验模型类型、连接地址、参数和向量维度，返回原版格式。
3. 实现连接检查和明确的超时、认证失败反馈。
4. 接入真实模型提供商时，通过同一服务调用边界替换测试实现。
5. 密钥只保留在后端；列表响应、日志和前端构建产物中不得出现明文密钥。

**产出：** 模型路由、模型服务、仓储、假模型测试夹具，以及前端模型配置页可用的接口。

**过关条件：** 保存配置后重启服务仍可读取；密钥不泄漏；失败能显示原因。真实模型测试需显式设置 `RUN_REAL_LLM=1` 和测试凭据，不混入默认测试套件。

## 7. `S5`：完成第一个真正的业务模块——知识库

知识库先理解成“有一组规则的资料容器”。名称、模型关联、分块设置和权限共同决定它怎样处理资料。

从原版知识库接口选“创建 → 列表 → 详情 → 修改 → 删除”这一条完整路径。每做一个接口，都连上前端同一个按钮，不积攒到最后才联调。

以“创建”为例，页面传入名称和配置；路由把字段交给服务；服务确认模型归属和权限；仓储在事务内保存；路由按原版格式响应。这里暂时无需上传文件，就能练会分层。

**新增位置：** `app/api/v1/routes/knowledge_bases.py`、对应请求模式、`app/services/knowledge_bases.py`、`app/repositories/knowledge_bases.py`。这些是目标文件名，不要求与原版文件名相同。

**过关条件：** 刷新后还能打开新知识库；分页及空结果与原版一致；越权读写被拒绝；删除有明确影响范围。后续添加文档和向量后，必须补测删除的关联清理，不能继续沿用“只删一行”的练习实现。

## 8. `S6`：把文件变成可检索的资料

上传成功只代表收到文件，不代表已经理解文件。完整链路是：接收文件 → 保存原件 → 提取内容 → 切成片段 → 生成向量 → 建立索引 → 更新状态。

### 8.1 用一份短文本走完链路

先上传自己写的几段文本，观察每一步结果。一个片段称为 `chunk`，要保留所属文档、顺序和来源位置，否则聊天引用就无法打开原文。

原版上传路由包括 `POST /api/v1/knowledge-bases/:id/knowledge/file`，其中 `:id` 是占位符。字段名称、上传表单及返回体以原处理器和页面请求为准，不另造一个不兼容的 `/upload`。

在 `app/storage/` 管原文件，在 `app/services/` 编排流程，在 `app/integrations/` 连接解析器。先做文本教学实现，再参照 `docreader/README.md` 接入已有解析服务，逐一验证 `PDF`、办公文档、图片等基线支持的格式。不要一次重写整个解析器库。

### 8.2 为什么要有后台任务

用户不应一直等待一个上传请求完成全部解析。请求接收后记录任务，后台执行，页面查询状态。早期可以用单进程练习，但任务状态必须持久化，并明确重启后怎样恢复；正式使用前接入 `Redis + ARQ` 等可靠任务执行机制。

原版文档解析状态定义在 `internal/types/knowledge.go`，包含 `pending`、`processing`、`finalizing`、`completed`、`failed`、`deleting`、`cancelled`。不要用自定义的 `queued/succeeded` 替换对外字段；内部队列可以有自己的状态，但应明确映射。

先完成正常路径，再逐个加入：重复执行不重复入库、失败可重试、删除或取消后不再写回成功状态、重启恢复、任务归属校验。队列实现可以换，前端契约和这些行为不能丢。

**过关条件：** 能从页面看到上传和解析状态，查看原文和片段；大文件限制、类型校验、恶意文件名、解析失败、取消和重复处理均有检查。新任务不能使用用户提交的路径直接写服务器磁盘。

## 9. `S7`：先证明“找得对”，再让模型回答

关键词检索找字面相似，向量检索找含义相似，混合检索把两种结果合并，重排再筛选。先用固定资料测结果，别让聊天模型掩盖检索问题。

准备三份互相容易区分的资料，例如报销、休假和设备申领。提问“年假怎么申请”，先检查休假资料是否进入结果，再检查来源标识、片段位置和返回数量。

1. 对照原版检索请求字段和结果结构实现接口。
2. 从确定性向量实验开始，理解距离和排序；随后连接实际向量存储与模型。
3. 合并重复候选，按原版规则过滤、排序和限制数量。
4. 在查询或候选读取阶段执行知识库访问控制，避免其他租户内容进入重排、模型或日志。
5. 测试空查询、无结果、模型不可用、向量维度不匹配和未授权知识库。

**产出：** 检索服务、检索接口、固定语料和排序测试，以及原版检索入口／命令面板的联调。

**过关条件：** 同一固定输入可得到可解释结果；引用能定位原文；查询范围不会扩大到未授权知识库。小数据内存计算是教学练习，不能据此宣称生产搜索能力已经等价。

## 10. `S8`：让回答逐段出现，并能重新打开

检索增强生成就是“先找资料，再带着资料回答”。会话保存多轮对话，消息保存每次输入和输出，引用保存答案来自哪里。

### 10.1 先普通回答，再流式回答

先让后端完成“读取资料 → 调用假模型 → 保存问答 → 返回”，验证刷新页面后消息仍存在。然后将响应改成逐段推送，保持同样的权限和持久化要求。

`SSE` 可以理解成服务器保持一个连接，不断寄来小纸条。网络读到的一块字节不一定是一条纸条：一条事件可能被拆开，几条事件也可能一起到达。

原版协议尤其要注意：**外层事件名为 `message`，业务类型放在数据的 `response_type` 字段里。** `answer`、`references`、`complete` 等不是这里可以自行替换的外层事件名。参考 `internal/types/chat.go` 中的 `StreamResponse` 和 `internal/handler/session/stream.go`。

下面仅演示外层格式，不代表一轮完整的业务事件序列：

```text
event: message
data: {"id":"example","response_type":"answer","content":"你好","done":false}

```

完整响应还可能包含会话标识、回答消息标识、`knowledge_references`、工具数据和用量。记录原版实际事件顺序与结束语义，再实现；不要把服务内部的事件总线名称直接当作浏览器协议。

### 10.2 一次回答要收好尾

1. 校验会话所有者、当前租户和资料访问权限。
2. 保存用户消息，再开始检索和生成。
3. 发送增量结果，让前端累积显示；引用按原版字段关联。
4. 正常完成后持久化完整回答和状态。
5. 出错或主动停止时保留合理的已生成内容，结束相关模型调用并释放任务资源。仅浏览器断开时先释放该连接资源，后台生成是否继续按原版停止与恢复策略处理。
6. 区分关闭浏览器连接与主动停止生成；原版有继续接收活跃流的入口，后续恢复行为也要补齐，不能一律丢弃运行。

**新增位置：** 会话与消息仓储、聊天服务、流式路由、`tests/e2e/` 中的持久化流程和流式协议检查。

**过关条件：** 登录 → 建库 → 上传 → 检索 → 问答 → 刷新恢复完整跑通；停止、上游失败、引用越权、跨网络块解析都有验证。这里只是第一个端到端版本，尚不能标记“完整复刻”。

## 12. `S10`：在干净环境证明系统能独立工作

到这里才把本地教学环境提升为可部署系统。`SQLite`、假模型和单进程实验的结果不能替代真实依赖验收。

1. 在独立 `PostgreSQL` 测试库运行原版结构兼容测试、事务测试和业务流程。
2. 验证后台任务的重启恢复、幂等、重试上限、取消和失败查询。
3. 对接选定存储与向量服务，验证上传、下载、权限及删除一致性。
4. 运行真实模型和真实解析器验收，记录版本、配置和限制，报告中去除密钥。
5. 配置反向代理的流式响应、长连接和 `WebSocket` 转发；验证部署后的行为，而非只验证开发代理。
6. 检查日志脱敏、请求标识、审计、限流、依赖就绪检查、备份恢复和版本回退。
7. 从干净环境按文档启动新前后端，逐项执行功能清单和视觉对照。

原版只用于对照；新系统正常提供服务不应依赖旧 `Go` 业务服务。复用独立 `docreader` 是明确的解析依赖，需要一同写入部署说明。

**最终证据：** 功能矩阵全部有结果、数据库兼容结果、真实依赖测试、部署步骤、恢复演练和前端截图差异记录。后端测试通过只证明接口行为，界面是否一致需要结合前端指南验收。

## 13. 每次学习只推进一个小闭环

按“读一条原版流程 → 记录契约 → 写最小测试 → 实现 → 连页面 → 保存证据”的顺序做。不要把阅读一章当作通过一章。

在后端目录、虚拟环境已激活时，运行当前已经建立的检查：

```sh
python -m pytest -q
python -m ruff check .
```

随着测试数量增长，先运行改动相关测试，通过后再执行本阶段需要的回归。真实模型测试保持单独开启。阶段验收脚本只有在自己创建并说明参数后才使用；本文没有提供一个已经存在的“全部完成”命令。

每次结束记下：今天新增的接口、看到的页面结果、故意制造的一次失败、测试证据、未完成项和下一步。今天从 `S1` 开始时，只需交付健康接口和测试，并能回答：“浏览器、后端、数据库各负责什么？”

本文是源码核对后的实施教程，不是已完成报告。本次将 `S1` 的工程配置、健康接口和测试提取到临时目录实际安装验证，结果为 `1 passed`，`Ruff` 检查通过；依赖给出测试客户端与异步夹具配置的弃用提示，不影响这次检查结果。未在本仓库创建新的 `Python` 应用，也未执行后续业务和真实依赖验收。
