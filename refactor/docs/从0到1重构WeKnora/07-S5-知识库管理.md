# `S5`：把知识库管理做成第一个完整业务模块

[目录](./00-目录.md) · [上一章](./06-S4-模型配置与网关.md) · [下一章](./08-S6-上传解析与索引.md)


## 1. 本章的用户故事

用户登录后创建一个知识库，修改设置，打开详情，刷新后仍能找到它，最后按权限和原版规则删除它。知识库是带有模型、解析、检索和权限配置的资料容器，不只是一个名称。

**前置条件：** `S3` 身份与租户可靠；`S4` 有可用模型配置；`S2` 数据持久化与事务已经通过。

```mermaid
flowchart LR
    A[创建弹窗] --> B[前端校验和提交]
    B --> C[鉴权与可信租户]
    C --> D[业务校验与模型关联]
    D --> E[事务保存知识库]
    E --> F[按原版格式返回]
    F --> G[列表更新并进入详情]
    G --> H[刷新后重新查询]
```

## 2. 原版入口与待创建文件

原版路径从仓库根目录起：

| 原版入口 | 读什么 |
| --- | --- |
| `frontend/src/views/knowledge/KnowledgeBaseList.vue` | 列表、创建、卡片与导航 |
| `frontend/src/views/knowledge/KnowledgeBase.vue` | 详情、设置和空文档状态 |
| `frontend/src/api/knowledge-base/index.ts` | 知识库请求及响应 |
| `internal/router/routes_knowledge.go` | 路由、方法和资源权限 |
| `internal/handler/knowledgebase.go` | 参数、返回、设置更新 |
| `internal/types/knowledgebase.go` | 配置与实体含义 |
| `internal/application/repository/knowledgebase.go` | 数据查询、更新和删除 |

目标后端位置相对于 `refactor/python/backend/`：`app/api/v1/routes/knowledge_bases.py`、`app/api/v1/schemas/knowledge_bases.py`、`app/services/knowledge_bases.py`、`app/repositories/knowledge_bases.py`。

目标前端：`src/api/knowledge-base/`、`src/types/`、`src/views/knowledge/`。局部表单状态在组件，跨页共享数据确有需要时才进入状态仓库。

详细状态和文件上传将在下一章完成；本章先把无文档知识库的管理闭环做稳，但删除设计必须预留已有原版关联语义，而不是提前改变契约。

## 3. 按顺序完成任务

### `S5.1` 把创建到删除拆成操作契约

**输入：** `S0` 知识库记录、原版页面与调用。

1. 分别记录创建、列表、详情、修改、删除的请求与响应。
2. 对照知识库类型、模型关联、解析与检索设置，建立必填与默认值表。
3. 记录分页、筛选、排序、空列表以及资源不存在的行为。
4. 记录谁能查看、谁能修改、共享资源有哪些例外，不能假定所有资源只按当前租户等值查询。
5. 核对不同更新方法的含义，未提交字段不能误清除。

#### 每个操作都整理到可直接写请求模式

先只选择普通知识库的一份最小合法样例；不同类型的字段差异随后逐个补齐，不用一份随意缩减的请求代表全部创建方式。

1. 从前端创建函数找到请求方法、路径、正文，再到处理器核对必填、默认和失败条件。
2. 把每个字段分为用户输入、服务端生成、关联对象或派生展示；服务端生成的身份不能让浏览器随意指定。
3. 记录列表与详情各自响应，哪些字段只在详情存在，编辑必须以哪份数据为准。
4. 对修改请求记录缺失字段、空值、清空操作的差别；对删除记录响应后资源是否已经不可访问。

**交付：** `app/api/v1/schemas/knowledge_bases.py` 与前端类型可依据相同样例建立。对不清楚的字段回到调用和处理器，不凭名称猜含义。

**结果：** 每个页面操作有对应的接口与数据规则。

**检查：** 前后端依据同一份契约，避免页面自己猜字段默认值。

### `S5.2` 先完成列表和详情的后端查询

**输入：** 可信身份、资源访问规则与数据库映射。

1. 仓储负责列表、详情及必要条件；权限在可信上下文下检查。
2. 按原版实现分页、排序与响应结构。
3. 返回必要的模型和配置数据，避免泄露关联凭据。
4. 对不存在、已删除、无权读取等情况返回原版规定结果。
5. 用独立夹具创建少量测试记录，覆盖空列表和多页边界。

#### 列表与详情先通过接口测试

仓储返回业务需要的数据；服务决定是否允许查看；响应模式控制最终对外字段。分开这三步，避免直接把带模型凭据的关联实体返回浏览器。

1. 在 `app/repositories/knowledge_bases.py` 先做详情查询，输入可信范围与资源标识，输出记录或明确不存在结果。
2. 服务补资源读取授权，按原版处理共享与管理员例外；不能仅凭客户端租户参数查询。
3. 列表先应用授权范围、过滤及删除条件，再排序分页；总数与列表必须使用一致条件。
4. 路由调用服务并序列化，比较实际字段、时间、空值与原版样例，确认模型关联只返回允许信息。
5. 夹具准备甲空间两条、乙空间一条，以及已删除或不可见样本；查询甲时断言乙的数据和总数都不会泄露。

**卡点：** 第一页有数据但下一页重复，先检查稳定排序与分页条件；详情可以读但列表没有，比较过滤和授权规则，不先删除权限条件。

**结果：** 不依赖界面就能查询正确范围内的知识库。

**检查：** 不能只验证查询成功，还要断言不应返回的记录没有出现。

### `S5.3` 实现创建并验证模型关系

**输入：** 一份合法创建请求和 `S4` 模型配置。

1. 请求模式校验字段，服务执行业务限制与权限判断。
2. 检查关联模型是否存在、是否可用、类型是否匹配以及是否有权使用。
3. 在事务中保存知识库及必须同步创建的关联数据。
4. 返回原版结构中的真实资源标识，不生成只存在于浏览器的假标识。
5. 对无效模型、越权关联和重复提交进行边界验证。

#### 创建请求从参数走到提交成功

在 `app/services/knowledge_bases.py` 先做一个创建方法。输入是可信身份与已校验请求，输出是已成功保存的知识库结果；目标方法名可按现有工程约定确定。

1. 请求模式先拒绝结构错误，服务再处理名称、类型和配置组合的业务规则。
2. 用 `S4` 的授权模型读取能力检查每个关联：存在、类型匹配、当前用户允许使用；不要另外复制一套只按主键查询。
3. 验证通过后开启或加入已约定事务，将主体与必要关联交给仓储；标识生成使用原版兼容机制。
4. 仓储必要时刷新取得标识，不独立提交；服务确认事务提交成功后才返回成功结果。
5. 测试拿返回标识调用详情，再关闭会话或重启服务重读，确认名称、归属和配置都保存了。
6. 最后才把创建按钮连接到该接口，不能用浏览器临时标识代替后端结果。

**失败检查：** 不存在的模型、另一空间模型、类型错误模型、提交失败分别执行，查询库中均无本次残留；重复提交的处理按原版规则验证，不自行承诺幂等。

**结果：** 创建后通过详情接口可以读回同一资源。

**检查：** 创建失败不留下半完成记录，关联规则不能只在前端验证。

### `S5.4` 实现修改与删除规则

**输入：** 原版设置更新、资源引用及删除行为。

1. 按原版区分未提交字段、空值和显式重置。
2. 修改影响后续解析或索引的设置时，保留原版提示和重建要求，不假装旧数据自动更新。
3. 删除前再次检查权限和资源状态，定义关联任务、文件、向量的处理责任。
4. 当前无文档闭环先验证数据库删除；`S6` 接入文档后补齐真实关联清理测试。
5. 失败时保留可诊断状态，禁止只返回成功却留下未知半删除结果。

#### 修改按字段意图合并，删除按生命周期执行

部分更新的核心是“没提交”与“明确改掉”不同。直接拿表单默认空值覆盖实体，会把用户没有编辑的配置一起清掉。

1. 服务先授权并读取完整当前记录，区分请求实际提交的字段，只对允许修改部分执行合并。
2. 对变更的模型和配置重新校验；不能因为原来合法就跳过新关联授权。
3. 保存成功后用新会话读取详情，比较修改字段变化、未提交字段保留、显式清空符合原版。
4. 删除单独进入删除服务路径，检查状态和权限；按原版同步或异步语义返回，不能提前承诺关联文件全部清理。
5. 先验证空库删除与重复访问；在 `S6` 补文档后，复测任务、源文件、块、索引及共享关系的处理。

**失败检查：** 更新失败保留旧配置；删除关键清理失败保留可诊断状态。列表重新读取后不再出现原版已不可见的资源，而不是只把本地卡片移除。

**结果：** 修改可读回，删除符合原版业务语义。

**检查：** 已被删除的资源不会继续从列表或缓存出现。

### `S5.5` 先复刻静态列表，再接真实数据

**输入：** 原版卡片、列表、空态和布局截图。

1. 用固定数据画出一张卡片、列表布局和空状态。
2. 使用原版图片、图标和 `TDesign` 控件，工具类控制布局与间距。
3. 接入真实列表，分别显示加载、成功、空态、失败与重试。
4. 详情路由保存真实知识库标识，直接刷新地址也能恢复。
5. 卡片点击、操作菜单、焦点与键盘行为逐项对照。

#### 页面先接只读数据，再做写操作

在 `src/api/knowledge-base/` 封装列表和详情请求，在页面保存当前查询条件与显示状态；别让每张卡片自己请求完整知识库列表。

1. 先用一条脱敏样例确定卡片展示字段及原版布局，再接真实列表函数并删除运行时的固定假数据。
2. 请求开始设为加载；成功且无记录显示空态；失败保留错误反馈，不能通过空数组假装成功。
3. 卡片以真实知识库标识作为稳定身份，点击后按原版路由进入详情；数组下标不作为资源编号。
4. 详情从路由参数读标识并发请求，直接粘贴地址或刷新也能加载，不依赖前一个页面传来的内存对象。
5. 加载失败、无权访问和不存在分别按契约显示，避免页面一直等待或展示另一条旧记录。

**具体检查：** 先空库，再一条，再多页；分别刷新列表和详情。页面空白先看响应层级与字段映射，找不到接口先检查前缀和代理，不同时改多处。

**结果：** 页面显示真实数据，布局也有原版依据。

**检查：** 不为让截图好看而隐藏错误提示或分页边界。

### `S5.6` 接通创建、编辑和删除交互

**输入：** 后端管理接口与原版弹窗。

1. 表单字段、默认值和类型切换按契约显示。
2. 提交时显示加载并防重复；失败保留用户输入，成功后关闭或导航遵循原版。
3. 编辑加载真实详情，避免只用列表的简化字段覆盖完整配置。
4. 删除使用原版确认方式，失败时卡片保留并显示原因。
5. 无权限状态与服务端一致，但任何隐藏按钮都不能替代服务端授权。

#### 表单草稿与服务端记录分开

创建和编辑表单都是未保存草稿。直接绑定列表对象会让用户还没保存，卡片就变了，取消时也无法恢复。

1. 创建时根据原版默认值建立草稿；编辑时先读取详情，再复制允许编辑字段。
2. 提交入口先处理前端提示，再设置提交中；原版后端仍执行完整校验。
3. 成功时使用后端返回身份并更新或重新查询列表，导航与关闭弹窗按原版顺序执行。
4. 失败时保留草稿、显示错误并释放提交状态；取消则丢弃草稿，不发送写请求。
5. 删除确认后再发请求；明确成功或受理后按契约更新状态，失败时不能先把资源永久从页面移除。

**具体检查：** 编辑名称后取消，重新打开仍是旧名称；提交失败后输入还在；成功刷新仍显示新名称。回车和点击必须共用同一提交逻辑，避免两次写请求。

**结果：** 浏览器能完成完整增删改查。

**检查：** 刷新页面后结果不变，取消弹窗不会误提交。

### `S5.7` 处理缓存与迟到响应

**输入：** 写操作成功后的列表更新需要。

1. 首先用直接重新查询保持正确，再按实际共享需求引入缓存。
2. 写操作后使对应资源列表和详情失效。
3. 请求按租户、资源与查询条件区分，不能复用另一空间的快照。
4. 让旧列表请求延迟，在删除或切空间后才返回，验证它不能回写旧记录。
5. 参考原版 `resourceCache.ts`、`versionedRequest.ts` 的机制，不照搬无关全局数据。

#### 先保证旧结果不能覆盖新状态

缓存是为了复用之前拿到的数据；代际是判断这个结果是否还属于当前页面状态的标识。没有缓存需求时，先用直接重查与请求有效性检查完成正确流程。

1. 发列表请求时记录当前租户、查询条件和请求代际；返回后确认仍匹配才更新页面。
2. 新查询、切空间或资源写操作使旧代际失效；必要时中止传输，但不能仅依赖取消一定成功。
3. 创建、编辑、删除成功后更新相关列表和详情，重新查询的结果以最新有效代际为准。
4. 引入共享缓存时，键包含权限范围及查询条件，失效同时覆盖相关列表和详情；不能只缓存资源标识。
5. 测试让旧列表先发后返回：发旧列表 → 完成删除 → 加载新列表 → 放行旧列表，资源不得复活。

**再测一次：** 旧空间详情等待期间切空间，随后放行旧响应，新空间不能短暂出现旧正文。出现问题先检查更新入口是否都做有效性判断，而不只检查网络是否取消。

**结果：** 快速操作下数据仍与服务器一致。

**检查：** 页面不出现“删掉又回来”或切空间后短暂显示旧卡片。

### `S5.8` 完成功能与视觉验收

**输入：** 完整管理闭环与 `S0` 截图。

1. 用普通用户和管理员分别走成功与拒绝操作。
2. 覆盖创建、刷新、编辑、删除、网络失败与取消。
3. 对比列表、创建弹窗、详情、错误和暗色状态的截图。
4. 编写核心接口流程与浏览器回归，避免只测试模拟函数被调用。
5. 将尚未完成的高级知识库设置写入 `S9` 清单，不把“有详情页”当作全部设置完成。

#### 用同一条真实资源串起验收

选择固定名称“采购规则”、已授权的测试模型和普通用户；每一步使用上一步服务端返回的标识，不能靠不同模拟数据拼出看似完整的流程。

1. 接口测试创建、详情、更新、重读、删除、再次读取，逐项断言字段、状态码和持久结果。
2. 用另一用户替换凭据重复读取和修改同一标识，验证拒绝且数据库未改变。
3. 浏览器从列表创建后进入详情，刷新再编辑，取消一次再保存，最后删除；记录网络请求与页面实际结果。
4. 注入保存失败与迟到响应，检查草稿、列表和当前空间状态；这些验证与截图对照分开记录。
5. 对同一数据、角色、视口和主题截取列表、弹窗、详情与错误状态，列出差异，别用静态样例掩盖加载或失败。

**本阶段结论：** 可以确认无文档知识库管理闭环；未接入的高级设置和有文档删除仍明确待验收，不能把阶段结论扩大为整个知识管理模块已完成。

**结果：** 第一项业务模块具备可重复的前后端验收。

**检查：** 测试验证资源持久化与权限，截图验证外观，两者都要有证据。

## 4. 成功与失败案例

**成功：** 创建“采购规则”知识库 → 打开详情 → 修改名称 → 刷新 → 删除 → 再次查询确认不再可用。

**失败：** 选择不存在或无权使用的模型创建知识库，后端拒绝且不留记录，前端保留表单并显示错误。再用另一个空间的用户请求该库，验证服务端隔离。

## 5. 过关清单与排错

- [ ] 列表、详情、创建、修改、删除符合原版契约。
- [ ] 模型关联与资源权限由服务端验证。
- [ ] 刷新后数据保持一致，失败写入没有残留。
- [ ] 页面覆盖空、加载、失败、弹窗、取消和无权限状态。
- [ ] 缓存失效与旧请求回写有验证。
- [ ] 视觉差异、待做设置和结果登记到[进度记录](./13-进度与验收记录.md)。

| 现象 | 优先排查 |
| --- | --- |
| 创建后列表不更新 | 响应结构、列表失效、查询条件 |
