# `S0`：先知道要复刻什么

[目录](./00-目录.md) · [上一章](./01-总路线与学习方法.md) · [下一章](./03-S1-工程初始化与页面骨架.md)

## 1. 本章要解决什么

你准备复刻一家资料室，第一步是看清它怎样接收资料、管理用户和回答问题。基线就是保存“原版这一刻是什么样”的证据，之后每一项实现都能与它比较。

本章不开发业务代码。完成后，应能把“功能和样式一样”拆成可检查的页面操作、接口约定、数据关系和截图，而不是一句模糊目标。

**前置条件：** 能打开仓库、使用终端、阅读简单的对象和表格。尚不能运行原版时，先做源码清单；真实行为与截图保持“待采集”。

```mermaid
flowchart LR
    A[固定原版版本] --> B[操作一个功能]
    B --> C[记录页面和请求]
    C --> D[追到服务与数据]
    D --> E[形成验收样例]
    E --> F[以后用新实现复现]
```

## 2. 准备哪些材料

以下原版路径相对于仓库根目录 `WeKnora/`：

| 要找的答案 | 原版入口 |
| --- | --- |
| 页面有哪些入口 | `frontend/src/router/index.ts`、`frontend/src/views/platform/index.vue` |
| 按钮发出什么请求 | `frontend/src/api/` |
| 请求在哪校验 | `internal/router/`、`internal/handler/` |
| 业务规则在哪里 | `internal/application/service/`、`internal/application/access/` |
| 数据长什么样 | `migrations/`、`internal/types/` |
| 外观来自哪里 | `frontend/src/assets/theme/`、`frontend/src/assets/img/` |

在本目录下逐步建立 `实践记录/`，只存脱敏样例和学习证据。阶段状态统一写入[进度与验收记录](./13-进度与验收记录.md)，不要再维护另一套完成率。

| 建议证据文件 | 保存内容 |
| --- | --- |
| `实践记录/S0/rebuild-baseline.md` | 提交号、运行模式、端口、角色、浏览器与主题 |
| `实践记录/S0/feature-parity.md` | 功能入口、操作、依赖、结果、状态 |
| `实践记录/S0/api-contract.md` | 成功、失败、权限、分页和空值样例 |
| `实践记录/S0/database-contract.md` | 表、字段、约束、关联、迁移来源 |
| `实践记录/S0/visual-parity.md` | 截图条件、文件位置、差异与复验 |

以上是待创建材料，不表示已经采集完成。

## 3. 按顺序完成任务

### `S0.1` 固定工作位置和参照版本

**输入：** 当前仓库和终端。

1. 在 `refactor/` 执行下面命令，记录输出。
2. 标出已有未提交修改，后续只修改本次任务文件。
3. 记录原版当前提交；存在源码本地修改时，将其作为额外差异记录，否则同一提交号也无法复现页面。
4. 原版升级后重新建立基线，不混用新旧截图。

```sh
pwd
git rev-parse HEAD
git status --short
```

**看得见的结果：** 基线文件明确指出“我复刻的是哪个版本”。

**检查：** 另一人能根据提交与差异记录找到相同源码，不需要猜测你说的是哪个原版。

### `S0.2` 把原版运行与新工程位置分开

**输入：** [本地部署说明](../operations/WeKnora本地部署与使用说明.md)。

1. 按现有部署说明选择一种原版运行模式，记录启用功能和外部依赖。
2. 新工程仍放在 `refactor/python/backend/` 与 `refactor/python/frontend/`，当前尚待创建。
3. 原版与新后端都可能占用 `8080`。分别运行或明确设置不同端口，所有对照请求记录目标地址。
4. 原版数据库仅作参照；未来新工程使用独立学习数据库，不让练习删除操作碰到原数据。

**看得见的结果：** 能明确说出当前浏览器连接的是原版还是新服务。

**检查：** 停掉目标服务后，对应请求确实失败；没有误连另一实例。

### `S0.3` 沿一个用户故事记录功能

**输入：** 原版登录和知识库入口，以及[功能地图](./92-知识词典与原版功能地图.md)。

1. 先选“登录后创建知识库”这个小故事。
2. 记录进入页面、点击创建、填写字段、提交、打开详情的每一步。
3. 再做名称为空、取消弹窗、重复点击和无权限操作，记录原版实际反馈。
4. 将其余功能组列入清单，暂时不逐个深挖；进入对应阶段再展开。
5. 把设置弹窗、命令面板、嵌入页和后台任务也列入，不能只统计路由页面。

**看得见的结果：** 一组可以照着重复的操作说明。

**检查：** 功能条目写到具体操作，例如“删除失败保留卡片”，而不是只写“知识库完成”。

### `S0.4` 为每个操作留下接口契约

**输入：** 浏览器网络面板及对应 `frontend/src/api/` 调用。

1. 记录请求方法、完整路径、参数、请求体、响应状态与响应体。
2. 敏感请求头只记录名称和格式，删除真实令牌、密码与密钥。
3. 回到原版路由、处理器和类型，确认必填字段、默认值、分页、时间、空值与错误结构。
4. 对照成功和失败样例，标记“实际采集”与“仅源码推断”。
5. 不强行将所有响应包成新的统一 `data` 格式；兼容要求保留每个原版契约。

**看得见的结果：** 新实现可以直接以样例写契约测试。

**检查：** 不仅路径相同，字段名、数组/对象结构、状态码和权限边界也有记录。

### `S0.5` 追踪数据落在哪里

**输入：** 创建知识库涉及的类型、仓储和迁移。

1. 从处理器跟到服务和仓储，找出实际写入的表。
2. 阅读建表与后续迁移，补齐字段最终状态，不能只抄最早的建表语句。
3. 记录资源如何关联当前租户与模型，删除时影响哪些关联记录。
4. 分别记录 `SQLite` 和 `PostgreSQL` 的差异，不把一种数据库的约束推断为另一种已通过。

**看得见的结果：** 一张“页面字段 → 接口字段 → 数据字段”的对应表。

**检查：** 每个字段能指出源码或迁移依据；不能凭界面文字创造新数据库字段。

### `S0.6` 固定视觉比较条件

**输入：** 原版页面与主题文件。

1. 固定浏览器、窗口、缩放、语言、主题、字体与测试数据。
2. 保存列表、空态、错误、创建弹窗、选中和禁用等状态截图。
3. 从计算样式记录主要尺寸与颜色；颜色引用原版变量，图片使用原素材。
4. 为窄屏、亮色与暗色分别留样例；没有实际验证的状态继续标记待采集。
5. 在对照表中写明 `TDesign` 与锁文件版本，后续升级不能悄悄改变基线。

**看得见的结果：** 新页面可以在相同条件下拍图比较。

**检查：** 不是只检查绿色相同，还检查文字换行、间距、边框、图标和交互状态。

## 4. 成功与失败练习

**成功练习：** 请另一人照操作记录创建知识库，核对请求字段、返回数据及截图。对方不需要你在旁解释隐含步骤，记录才足够完整。

**失败练习：** 故意换一个普通角色执行只有管理员可做的操作。记录前端入口与后端拒绝结果；没有账号环境时标记待验，不伪造权限已通过。

## 5. 验收与排错

- [ ] 参照提交、源码差异和部署模式清楚。
- [ ] 首批功能同时记录成功、失败与权限路径。
- [ ] 接口样例脱敏，响应结构来自原版。
- [ ] 表结构和视觉条件有可追溯来源。
- [ ] 全量功能清单已列出，未把主闭环当作完整产品。
- [ ] 证据位置及下一步已登记到进度记录。

| 卡点 | 处理方法 |
| --- | --- |
| 只看到页面，没有请求 | 检查是否使用缓存；在一次明确操作前清空网络面板 |
| 找不到某个页面路由 | 查弹窗、菜单、命令面板和全局组件 |
| 原版运行不起来 | 先记录源码证据，排查部署依赖，真实行为保持待验 |
| 文档与源码说法不同 | 以固定版本源码和实测为准，记录差异，不沿用旧完成率 |

进入 `S1` 前，用自己的话回答：为什么接口返回成功，还不能证明这个功能与原版一致？
